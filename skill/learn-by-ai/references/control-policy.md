# Teaching control policy

## Invocation boundaries

Start the full protocol for systematic learning, a materials-based course, adaptive diagnostics, layered practice, spaced review, progress updates, or continuation from a checkpoint. Do not start it for a standalone explanation or problem unless the user requests tracking.

## New-session orientation

After loading state, state only:

1. current node;
2. unresolved issue or due review;
3. today's observable target;
4. source(s) selected and why.

Then ask the checkpoint's unique opening question. Do not repeat a broad onboarding interview.

## Select the next node

Apply these gates in order:

1. A missing prerequisite blocks the active goal.
2. A due review is likely to block today's work.
3. The active unit has a natural unfinished continuation.
4. Choose the highest goal-weight reachable node.
5. Ensure the node and its assessment fit the remaining session capacity.
6. Prefer a package that combines concept, practice, and transfer/application.
7. Confirm accessible sources and assessment evidence exist.

Do not follow textbook page order mechanically. Do not skip a prerequisite because a later node appears more advanced or interesting.

## Route sources by need

| Need | Preferred role |
|---|---|
| Standard definitions and course spine | primary |
| Theorem conditions and rigorous proof | rigorous-deepening |
| Standard problems and exam patterns | problem-bank / exam |
| Counterexamples and exploration | problem-bank / rigorous-deepening |
| Modeling, simulation, or code | application / code |
| Comparison among methods | domain monograph / primary |

Filter the resource index first, then open only the relevant locator. If the preferred source is unavailable, name the failure and either use a labeled substitute or stop when fidelity matters.

## Teach one conceptual step

1. Present a concrete tension, prediction, counterexample, or application.
2. Ask for a discriminating judgment before explaining.
3. Identify what the learner's current concepts cannot yet resolve.
4. Define the new object, domain/codomain, notation, and assumptions.
5. Derive the core mechanism from the motivating problem.
6. Work one minimal example.
7. Connect one use case and one failure mode.
8. Ask a transfer check; do not end with only “Do you understand?”

## Classify the earliest breakpoint

Inspect in this order:

1. object confusion;
2. symbol, input/output, or shape confusion;
3. definition or quantifier error;
4. missing prerequisite;
5. missing mechanism or motivation;
6. omitted theorem condition;
7. method-selection error;
8. derivation-chain break;
9. algebra/computation error;
10. transfer failure;
11. expression/defense failure;
12. retention failure.

Respond to the first confirmed breakpoint:

| Breakpoint | Action |
|---|---|
| Object | Identify object, input, output, and containing set |
| Symbol/shape | Define each symbol and trace dimensions/types |
| Definition | Use a minimal positive, negative, and boundary example |
| Prerequisite | Pause the node and teach the shortest prerequisite chain |
| Mechanism | Re-derive from the original tension |
| Condition | Remove the condition and construct a counterexample |
| Method choice | Contrast two superficially similar but structurally different tasks |
| Derivation | Split only the failing equality or inference |
| Computation | Preserve the strategy and repair the computation |
| Transfer | Change one condition at a time with a near variation |
| Expression | Require object-condition-mechanism-conclusion narration |
| Retention | Use retrieval first; reteach only if structure is lost |

After two failures at the same breakpoint, add no new knowledge. Reduce the task one level, use a minimal concrete representation, and run one discriminating check. If it still fails, activate a prerequisite node and record the block.

## Distinguish stopping levels

- **Turn wait:** a question is pending. Continue the session after the answer. A normal turn wait needs no full commit; if the user explicitly stops at that boundary, update the checkpoint with the pending question and stop reason.
- **Node pause:** a natural stage ends or a prerequisite detour begins. Preserve the current node.
- **Session stop:** the planned package/time is complete at a natural boundary; the user asks to stop, summarize, or switch; the request is one-off; material essential to the current action is inaccessible; or the rest belongs in a separate prerequisite unit. Missing source files do not prevent a goal-based diagnostic when no source-specific claim is required.

At session stop, teach nothing new. Commit evidence and state, then provide a compact summary and the unique next opening question.
